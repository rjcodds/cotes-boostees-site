# Passation — cotes-boostees-site

Dernière mise à jour : 2026-09-13 (recoupement des posts manuels canal payant pour bet-analytix-sync).

## Contexte du projet

RJC Boost surveille les cotes boostées ("CB"/"GCB") de **Winamax** et **Unibet** via deux Cloudflare Workers (`workers/winamax-flash-boost/`, `workers/unibet-flash-boost/`), maintenus **en lockstep** (tout fix appliqué à l'un doit être mirroré sur l'autre, sauf mention contraire).

- Chaque worker scrape son bookmaker en continu (cron 1-5 min), détecte les nouvelles cotes boostées, et calcule une **"ligne de référence"** (terme introduit par l'utilisatrice cette session) en comparant contre 4 sources : **Pinnacle** (principale, quasi temps réel), **Piwi247** (exchange, perso), **Matchbook** (exchange, perso), **Oddsportal** (dernier recours, coûte un appel Browser Rendering — seulement tenté si Pinnacle+Piwi+Matchbook échouent tous).
- Deux canaux Telegram :
  - **Canal spawn** ("Spawn CB Uni / Wina") : monitoring privé, reçoit TOUTES les cotes détectées + toutes les lignes de référence disponibles (Pinnacle/Piwi/Matchbook/Oddsportal).
  - **Canal payant** ("Cotes boostées 🎯") : abonnés, ne reçoit QUE les cotes "éligibles" (mise max ≤ `MAX_STAKE_EUR` = 10€ côté Winamax), sans ligne de référence — juste l'annonce brute (voir `formatTelegramMessage`).
- **Betclic** n'a aucun scraper automatique : process 100% manuel (l'utilisatrice envoie une capture d'écran, je vérifie/poste à la main).
- **`workers/bet-analytix-sync/`** (nouveau) : journalise automatiquement dans [bet-analytix.com](https://app.bet-analytix.com) (bilan perso de l'utilisatrice) chaque cote du canal payant, comme pari "en attente" -- elle règle le résultat elle-même ensuite. **Pas appelé directement** par les workers principaux (ça a été essayé puis abandonné, risque de double-log) : c'est `/telegram-webhook` côté `unibet-flash-boost` qui écoute le canal payant en temps réel et appelle `bet-analytix-sync` via **service binding** (`env.BAX_WORKER`) à chaque nouveau post, qu'il soit automatique (flash Unibet, texte pur, `msg.text`) ou **manuel** (sélection quotidienne de l'utilisatrice parmi le digest -- image "COTE BOOSTÉE" + légende, `msg.caption` -- match/marché/cote illisibles en texte, retrouvés en recoupant bookmaker+heure de dispo avec `/digest-list-debug` de `winamax-flash-boost` via un second service binding, `env.WINAMAX_WORKER`). API bet-analytix entièrement reverse-engineered (pas de doc publique) -- **lire le README de ce worker avant d'y toucher**, il détaille deux pièges non-évidents (l'en-tête `sid` obligatoire mais pas documenté, et l'ID de bankroll de l'URL publique ≠ celui attendu par l'API).

> Les deux sections suivantes (landing page, création de contenu) n'ont pas été travaillées pendant cette session — reconstituées en lisant les fichiers du repo (`index.html`, READMEs des workers) pour donner une vue d'ensemble complète. À vérifier/compléter auprès de l'utilisatrice si des détails manquent, notamment sur les plans de contenu qui vivent surtout dans sa tête.

## Landing page (`index.html` à la racine, + pages annexes)

Page unique (~100 Ko), sections dans l'ordre : **hero** (accroche "On ne parie pas plus souvent. On parie quand le bookmaker se trompe.", preview de cotes en carrousel, mockup téléphone animé du parcours d'inscription) → **stats** ("On publie les vrais chiffres" : bénéfice cumulé, ROI, mise moyenne, cote moyenne — chiffres réels affichés en dur, probablement à mettre à jour manuellement) → **offres** (cartes Winamax/Unibet/Betclic, freebets/parrainage, grille de codes promo) → **outil** (renvoie vers le calculateur de conversion de bonus) → **communauté** (mise en avant du suivi Telegram en direct) → **transparence** → **FAQ**.

Fichiers annexes à la racine :
- `calculateur-bonus.html` — outil autonome de calcul de conversion de bonus/freebet en valeur réelle, lié depuis la section "outil" de la landing page.
- `monitoring.html` — dashboard interne (`noindex, nofollow`, donc pas destiné au public) de suivi des cotes Unibet/Winamax, distinct des workers eux-mêmes.
- `bankroll-chart.png`, `sitemap.xml`, `robots.txt` — actifs statiques classiques.

Pas de framework : HTML/CSS/JS vanilla dans un seul fichier. Pas de pipeline de build identifié pour la landing page (contrairement à `remotion/` qui a le sien).

## Directive permanente de l'utilisatrice (à appliquer sans qu'elle ait à le redemander)

> "C'est ce genre de réflexion et de construction que je veux que tu réalises sans mon intervention et ma vérification, tu dois essayer par tous les moyens possibles d'ajouter la ligne matchbook/pinnacle/piwi."

Avant de déclarer une ligne "non constructible" :
1. Chercher si le marché direct existe (même sous un autre libellé/seuil).
2. Sinon, essayer de le **construire** par somme (ex: sommer les scores exacts Oddsportal qui satisfont la condition) ou produit de marchés indépendants (approximation, toujours marquée `exact:false`, avec un avertissement affiché).
3. Documenter dans le code (commentaire) pourquoi c'est resté impossible si c'est vraiment le cas, avec la vérification effectuée (pas une supposition).

**Principe non négociable** : une ligne silencieusement **fausse** est bien pire qu'une ligne silencieusement **absente**. Plusieurs bugs cette session étaient exactement ça (mauvais championnat, mauvais marché) — toujours vérifier en direct après un fix, ne jamais supposer que ça marche.

## Gros chantiers de cette session (résumé technique)

Tout est commité et pushé sur `main`. Dans l'ordre chronologique (voir `git log` pour les messages complets, très détaillés) :

1. **Constructions "impossibles" résolues via Oddsportal** (score-summing) : `correctScore` étendu au tennis, `winsSet1ScoreMatch` (1er set X-Y ou Z-W), `winNotStraightSets` (vainqueur sans blanchir), `playersAllScore` (2 buteurs, Piwi), `playerWinsASet` (gagne au moins 1 set, n'importe lequel).
2. **Sweep genre féminin** : plusieurs regex n'acceptaient que le masculin (`joueurs` pas `joueuses`, `buteur` pas `buteuse`, `chacun` pas `chacune`, `1er/1ère` pas `premier`). Corrigé partout où trouvé. **Point de vigilance pour la suite** : tout nouveau marché ajouté doit accepter les deux genres dès le départ (foot féminin et tennis féminin sont déjà bien représentés dans les CB actuelles).
3. **Bug MLB "chacune au moins N runs"** : tombait dans le marché BTTS classique (>=1 run) au lieu du vrai seuil — ligne totalement fausse (1,12 au lieu de ~2,4). Nouveau type `bothTeamTotal` ajouté (Pinnacle/Piwi/Matchbook). + fallback "ligne la plus proche" quand le seuil exact demandé par le boost a bougé chez Pinnacle depuis sa création (`findTotal`, `findBothWinASet`).
4. **Bug Rinderknech "gagne et les 2 joueurs gagnent un set"** : tombait dans le mauvais marché (bothWinASet au lieu de winNotStraightSets) car le garde-fou anti-collision ne reconnaissait que "vainqueur et", pas "gagne et" (même sens, formulation Unibet différente). Corrigé.
5. **winAndTotal / winAndBtts sans marché combiné direct** (Paolini, PSG féminin) : ajout d'un repli en approximation (moneyline × total, ou moneyline × BTTS) quand le spécial combiné Pinnacle n'existe pas pour ce match précis — fréquent en compétitions féminines où Pinnacle propose moins de spéciaux combinés.
6. **Bug grave : Championship → mauvaise ligue (Égypte)**. Deux causes empilées :
   - `leagueCountryHint` exigeait "championship anglais" au lieu de juste "Championship" (le libellé brut réel envoyé par les bookmakers) → aucun indice pays → mauvais classement des championnats candidats.
   - Plus grave : quand le libellé ne matche pas fort, le code scanne **toute** la ligue du sport à l'aveugle jusqu'à trouver une ligue qui "resout" — sûr pour les paris à équipes nommées (une mauvaise ligue échoue juste à trouver les noms), **dangereux pour les combos "schedule"** (N matchs du jour, sans nom d'équipe) où n'importe quelle ligue avec assez de matchs "réussit" silencieusement. **Fix** : les combos schedule ne retombent plus jamais sur ce scan aveugle.
   - Ensuite trouvé un 2e bug qui empêchait même la VRAIE ligue de résoudre : Pinnacle liste les matchs de cartons/bookings ("Millwall (Bookings) - Wrexham (Bookings)") comme des matchups à part entière, faussant le décompte exact "N matchs du jour" attendu. Exclus.
7. **Bug Berrettini (best-of-5, "plus de 4,5 sets")** : le parser rejetait tout seuil ≠ 2,5 avant même de construire le pari (jamais mis à jour après le fix équivalent sur le combo multi-matchs). Une fois corrigé, `findBothWinASet` grappait quand même la mauvaise ligne (3,5 au lieu de 4,5, Pinnacle expose chaque ligne alternative comme un objet marché séparé). Corrigé.
8. **Bug critique de disponibilité** : `parseBoosts` (Winamax) plantait sur une entrée `null` dans `state.matches` (match retiré/en cours de chargement), et ce crash arrivait **avant tout le reste** dans `checkAndPost` → aucune mise à jour de snapshot, aucun post sur AUCUN canal pour chaque cycle où cette entrée traînait. Repéré via `/errors` (récurrent depuis ~24h). Un simple `if (!match) continue;` a suffi. **Vérifier `/errors` régulièrement en début de session** — c'est comme ça qu'on l'a trouvé, pas via une plainte utilisateur directe.
9. **Fix Socket.IO** : Winamax pousse les nouvelles cotes après le chargement initial de la page ; le scraper n'attendait pas que les entrées "réservées" (null) se peuplent. Ajout d'une 2e sonde bornée (3s) qui attend qu'il n'y ait plus de `null` dans `state.matches`.
10. **Bug K-League 1 (Winamax)** : `boost.league` restait `null` pour les combos "schedule" alors que Winamax met le nom du championnat directement dans le TITRE du match ("K-League 1", pas de paire d'équipes) — le code ne regardait que `state.tournaments[...]`, qui pointe vers un groupe générique ("Tous les paris") pour ce type de promo. Fix : repli sur `eventName` comme libellé de championnat quand `tournamentName` est absent, gardé par `splitTeams(eventName) === null` (jamais utiliser un vrai nom de match comme faux championnat). Unibet n'est pas concerné (son `league` vient d'un champ structuré séparé, indépendant de `eventName`).
11. **Bug `isRootMatchup` (grave, transversal)** : les sous-marchés Pinnacle "(Bookings)"/"(Corners)" (cartons, corners) partagent EXACTEMENT les noms des deux équipes et peuvent avoir `periods[].hasMoneyline: true` par erreur côté Pinnacle — sans garde-fou, `findRootMatchup` (et toutes les copies inline du même pattern dans le fichier) pouvait choisir ce sous-marché comme "racine" au lieu du vrai match dès qu'il apparaissait avant dans le tableau, faisant échouer silencieusement N'IMPORTE QUEL type de leg pour ce match (trouvé sur un margin "Manchester United gagne par au moins 2 buts", mais ça touchait potentiellement tout). Fix à la source : `isRootMatchup` rejette maintenant tout matchup dont un participant porte un suffixe entre parenthèses, peu importe `hasMoneyline`. **Bug important à garder en tête** : c'est la 2e fois que ce pattern "(Bookings)/(Corners)" casse quelque chose (1ère fois : comptage des combos schedule) — si un nouveau bug bizarre de "mauvais match/mauvaise ligue" apparaît, vérifier ce pattern en premier.
12. **Marché manquant : "TeamX gagne la 1ère/première mi-temps"** (victoire simple en 1ère mi-temps, sans autre condition) n'avait jamais été câblé comme parser à part entière — seuls les combos plus complexes ("gagne les deux mi-temps", "mène et gagne") géraient la période 1. Le catch-all générique refuse volontairement tout texte après "gagne" pour ne pas se tromper de marché, donc ce texte pourtant simple tombait dans le vide. Ajouté (`moneyline` + `period:1`), vérifié en direct sur Strasbourg (3,12).
13. **Incident réglé (hors code)** : un `/wrangler.jsonc` non commité était apparu à la racine du repo le 2026-09-06 (`assets.directory: "."`), cassant le déploiement des 4 workers (wrangler tentait d'uploader tout le repo, y compris les `node_modules`, comme assets statiques). Confirmé accidentel par l'utilisatrice et supprimé. Si un deploy échoue à nouveau avec une erreur "Asset too large" mentionnant un fichier `workerd` de ~135 Mo, c'est ce même symptôme qui revient — vérifier si un fichier `wrangler.jsonc`/`wrangler.toml` a réapparu à la racine du repo (en dehors des dossiers `workers/*/`).
14. **Marché manquant : "TeamX marque au moins N buts"** (entier, "au moins 4") jamais reconnu -- seule la formulation en ligne décimale ("marque plus de 3,5 buts") l'était, même marché `teamTotal` en réalité. Ajouté (`points = N - 0.5`). Vérifié en direct sur FC Barcelone (3,21).
15. **Cotes régulièrement manquées entièrement (jamais postées sur AUCUN canal)** — plainte récurrente de l'utilisatrice, confirmée réelle via `/errors` : côté Winamax, `checkAndPost` plante entièrement (0 retry) dès que le Browser Rendering partagé a un hoquet ("Unable to create new browser", "Unable to connect to existing session", "Navigating frame was detached", "Target closed", timeouts) -- ça arrive régulièrement en prod, et chaque occurrence saute TOUT le cycle de 5 min (aucune détection, aucun post, nulle part). Côté Unibet, un fetch non-ok échouait aussi silencieusement (`console.log` seulement, jamais `logError` -- `/errors` montrait 0 échec alors que rien ne prouvait qu'il n'y en avait pas). **Fix appliqué** : retry une fois (avec un court délai) sur les deux workers avant d'abandonner le cycle, + `logError` ajouté côté Unibet pour que ce type d'échec soit enfin visible. **Limitation qui RESTE, non résolue** : une cote dont toute la fenêtre de vie tombe entre deux passages du cron (5 min Winamax, 1 min Unibet) peut toujours être ratée sans aucune erreur — ce n'est pas un bug, c'est un compromis coût/couverture déjà documenté dans `wrangler.toml` (passer à un intervalle plus court coûterait plus cher en Browser Rendering). Si l'utilisatrice signale encore des cotes manquées après ce fix, différencier : erreur dans `/errors` au bon moment (= autre bug à chercher) vs rien du tout (= probablement ce compromis d'intervalle, à rediscuter consciemment si ça devient trop fréquent).
16. **Cotes republiées "Nouvelle cote" plusieurs fois sans changement (jusqu'à 3-4x/quelques heures)** — Winamax réémet parfois un nouveau `betId` (donc un nouveau `marketId` côté nous) pour EXACTEMENT la même promo (mêmes équipes, même marché, parfois même prix), sans rien changer d'autre visible. `diffBoosts` (canal spawn) et la clé de dédoublonnage `seen:` (canal payant) étaient toutes les deux basées uniquement sur `marketId` -> chaque rotation était traitée comme une cote entièrement neuve. Confirmé via le digest quotidien : "Taylor Townsend remporte au moins un set" postée 2x le même jour sous 2 `marketId` différents, texte identique. **Fix** : repli par contenu (`eventName::description`, fonction `boostContentKey`) dans les deux mécanismes -- un `marketId` inconnu n'est traité comme "add" que si aucune cote au texte identique n'existait déjà ; sinon c'est au pire une "Cote modifiée" (si le prix a bougé), sinon rien du tout. Appliqué en lockstep, mais **seulement confirmé côté Winamax** (digest Unibet ne montrait pas ce pattern sur les jours vérifiés) -- si ça persiste côté Unibet malgré le fix, `marketId` n'est peut-être pas la seule cause là-bas, creuser séparément.
17. **Doublons EXACTS (même marketId, même tout) postés coup sur coup sur canal spawn** — plainte encore présente après le fix #16, cause différente : `postMonitoringDiff` n'avait AUCUN garde-fou indépendant, il postait tout ce que `diffBoosts` calculait sans vérifier "est-ce que j'ai déjà vraiment envoyé ça". Si deux exécutions de `checkAndPost` se chevauchent (un tick de cron qui traîne + un `/run` manuel tombant au même moment, ou deux tocks de cron qui se recouvrent -- plus probable depuis le retry-sur-échec ajouté au point 15, qui allonge la durée d'une exécution), les deux peuvent lire le MÊME `prevBoosts` (snapshot pas encore réécrit par l'autre) et poster le même événement en double. **Fix** : garde KV (`spawnposted:{type}:{contentKey}:{newOdds}`, TTL 6h, même principe que le `seen:` du canal payant) vérifié avant l'envoi. **Non re-testé en conditions de course réelles** (aurait fallu déclencher deux exécutions qui se chevauchent en prod, pas fait pour ne pas spammer les vrais canaux) -- si des doublons EXACTS (même heure à la seconde près, même marketId) persistent après ce fix, la vraie cause est ailleurs, creuser plus profond (peut-être un vrai chevauchement de cron Cloudflare non empêché par une simple clé KV si les deux écritures sont simultanées à la milliseconde près).
18. **Nouveau chantier : `bet-analytix-sync`** (journalisation automatique du bilan). Voir la section dédiée plus haut et le README du worker. Reverse-engineering complet d'une API non documentée, fait à la main avec l'utilisatrice (F12 → Network, plusieurs allers-retours de captures d'écran) -- deux pièges non-évidents à retenir si ça casse un jour : (1) l'en-tête `sid` est obligatoire sur toutes les requêtes y compris le login, ressemble à un jeton de session mais est en fait un identifiant client stable généré une fois (pas régénéré par le serveur) -- une valeur arbitraire est rejetée, il faut la vraie valeur du navigateur de l'utilisatrice ; (2) l'ID de bankroll dans l'URL publique (1712234) n'est PAS celui attendu par l'API de création de pari, qui veut le champ séparé `id_bankroll` (4) trouvé dans la réponse de lecture. Testé de bout en bout avec un vrai pari créé et confirmé. Sport IDs autres que football (=1, confirmé) sont des suppositions non vérifiées -- risque faible si faux (catégorisation seulement, jamais les montants).
   - **Pivot d'architecture** (après un premier essai) : l'appel direct à `bet-analytix-sync` depuis la boucle de post du canal payant (`checkAndPost`) a été **retiré** des deux workers principaux -- risque de double-log si on l'avait laissé en plus d'un scraping du canal. Toute la logique vit maintenant dans `/telegram-webhook` (`unibet-flash-boost/index.js`), qui écoute déjà le canal payant pour autre chose (webhook Telegram existant).
   - **Le canal payant n'est PAS un simple filtre "mise ≤ 10€"** : l'utilisatrice sélectionne **manuellement**, chaque jour, parmi l'ensemble des cotes digérées, celles qu'elle juge "value", et les publie elle-même -- sauf les flash Unibet, publiées automatiquement par le bot. Deux formats de post à distinguer dans `/telegram-webhook` :
     - **Auto (texte pur, `msg.text`)** : nos propres posts ("Cote : X → Y", "Mise max : X€") -- parsés par `parseChannelPostForBax`, event/marché/cote lus directement dans le texte.
     - **Manuel (image + légende, `msg.caption`)** : une image "COTE BOOSTÉE ..." où vivent le match/marché/cote (illisibles par ce worker, jamais en texte), suivie d'une légende qui ne contient que le bookmaker, l'heure de dispo ("Dispo jusqu'à 18h00") et un tableau de mise par tranche de solde (20€/15€/10€/5€) -- la ligne marquée d'un **astérisque** est celle à utiliser dans le bilan. Parsé par `parseManualImagePostForBax` (bookmaker+mise+heure) puis recoupé avec `findWinamaxDigestMatch` contre `/digest-list-debug` de `winamax-flash-boost` (même heure de dispo = même item) pour retrouver event/marché/cote. Si 0 ou plusieurs items partagent la même heure, on renonce plutôt que deviner (loggé dans `/errors`).
     - `logDigestItem` (winamax-flash-boost ET unibet-flash-boost, les deux) stocke désormais aussi `kickoff` et `maxStake` par item (ajoutés spécifiquement pour ce recoupement -- absents avant le 2026-09-13, donc les digestitem antérieurs à cette date n'ont pas ces champs).
     - **Non géré pour l'instant** : posts manuels Betclic/Bet365 (aucun digest côté ces bookmakers pour recouper) -- loggés en erreur, à traiter le jour où l'utilisatrice en publie un premier (cf. son "je te préviendrai quand il y en aura une d'affichée").
   - **Audit "seulement 2 cotes sur ~20 loggées" (2026-09-15)** : `bet-analytix-sync` lui-même n'a JAMAIS d'erreur (chaque appel qu'il reçoit réussit) -- le problème est entièrement en amont, au parsing/recoupement. Deux vrais bugs trouvés en épluchant `/errors` d'`unibet-flash-boost`, les deux corrigés :
     - **Kickoff régulièrement `null`** : la légende écrit "Dispo jusqu'à 19h" (SANS minutes) quand l'heure tombe pile, mais la regex de `parseManualImagePostForBax` exigeait `\d{1,2}h\d{2}` (minutes obligatoires) -- kickoff jamais extrait, jamais recoupé. Fix : minutes rendues optionnelles, normalisées à "00" si absentes (pour matcher le format toujours-2-chiffres que stocke le digest via `formatKickoffTime`).
     - **Posts manuels Unibet jamais gérés** : l'utilisatrice publie aussi des GCB manuelles au format "🏆 COTE BOOSTÉE UNIBET" (pas seulement Winamax comme supposé initialement) -- explicitement rejetées ("pas de source de recoupement"). Fix : nouvelle fonction `findUnibetDigestMatch` (lit le KV local du worker directement, pas besoin de service binding vu que le digest Unibet vit dans ce même worker), routée selon `manual.bookmaker` dans `/telegram-webhook` et `/test-bax-parse`.
     - **Reste non récupérable rétroactivement** : les ~18 cotes manquées avant ce fix ne peuvent pas être reconstituées après coup (digestitem expire au bout de 2 jours, données déjà perdues pour les plus anciennes). ## Limitations connues, non résolues (ne pas re-découvrir à chaque fois)

- **Piwi tennis** : l'ID de compétition (`PIWI_COMPETITIONS_BY_SPORT.tennis`) est resté bloqué sur Cincinnati (semaine précédente) pendant tout l'US Open. Plusieurs tentatives de découverte automatique de l'ID correct ont échoué (`/customer/api/sports`, `/popular`, `/eventType/2`, `/menu`, `/search`, `/competition/2`, brute-force par proximité d'ID). **Reste à maintenir à la main chaque semaine**, comme `ODDSPORTAL_COMPETITIONS_BY_SPORT`.
- **Marché "buteur ou passe décisive"** (foot) : confirmé absent des 4 sources (44 marchés Piwi vérifiés sur un vrai match PSG-Monaco, rien). Pinnacle n'a de toute façon aucun prop joueur foot par match (déjà établi une session antérieure).
- **Digest KV** (`digestitem:`) ne garde que l'edge Pinnacle — jamais si Piwi/Matchbook/Oddsportal a résolu quelque chose. Pour savoir ce qui a VRAIMENT été posté sur canal spawn, utiliser `/test-monitoring-message` (rejoue le pipeline exact), pas le digest.
- **Boosts jamais "trackés" pour le refresh Pinnacle** : `pintrack:{marketId}` n'est créé que si `refLine` (Pinnacle) était non-null AU MOMENT DU POST initial. Si Pinnacle échoue au premier post puis se corrige plus tard (ex: après un fix de code), le message déjà envoyé sur canal spawn ne se corrige JAMAIS tout seul. Utiliser `/backfill-pinnacle` pour rattraper (poste un message "rattrapage" séparé si pas déjà tracké, ou édite le message existant sinon). **Réflexe à avoir après chaque fix de ligne de référence déployé en cours de journée** : lancer `/backfill-pinnacle` sur le(s) worker(s) concerné(s).
- **Winamax peut renvoyer une entrée `match` structurellement vide** (pas juste un délai Socket.IO) si le bookmaker n'a pas fini de peupler un marché tout juste sorti — vu sur la GCB Kvaratskhelia (PSG-Monaco, "marque ou passe décisive"), restée `null` plus d'une minute sans bouger. Dans ce cas, poster à la main (voir capture d'écran) plutôt que d'attendre le scraper.
- **Matchbook n'a pas de resolver pour `bothWinASet`** (total sets tennis) ni pour plusieurs autres types récents — pas forcément un bug, juste pas encore câblé.

## Outils de debug permanents (routes gardées exprès, utiles à la prochaine session)

Sur les deux workers sauf mention contraire :
- `/current` — snapshot actuel des cotes détectées.
- `/run` — force un cycle `checkAndPost` immédiat (utile pour vérifier qu'un fix marche sans attendre le cron).
- `/errors` — dernières erreurs loggées. **À vérifier en début de session**, c'est le meilleur moyen de repérer un bug silencieux en cours (comme le crash `mainBetId`).
- `/digest-list-debug?date=YYYY-MM-DD` — reconstruit la liste des cotes envoyées un jour donné depuis le KV (pas d'API Telegram pour lire l'historique du canal).
- `/test-monitoring-message?eventName=...&description=...&sport=...&newOdds=...&league=...` — rejoue EXACTEMENT le message qui serait posté sur canal spawn pour une cote donnée (toutes sources), sans attendre une vraie détection. Le paramètre `league` est important pour les combos schedule.
- `/test-pinnacle?a=...&b=...&d=...&sport=...&league=...` — teste juste Pinnacle, retourne aussi `line` (texte formaté).
- `/test-piwi-teams`, `/test-matchbook-teams`, `/test-oddsportal-teams` — équivalents pour les 3 autres sources.
- `/test-piwi-raw-markets?a=...&b=...&sport=...` — liste tous les noms de marchés Piwi disponibles pour un match (pour vérifier si un marché existe avant de deviner).
- `/test-pinnacle-raw-specials?a=...&b=...&sport=...` — liste TOUS les marchés spéciaux Pinnacle d'un match (`special.description` + participants) et, en plus, TOUS les matchups liés aux deux équipes sans filtrage (`allRelated`, avec `isRoot`/`parentId`) — utile pour vérifier l'existence d'un marché combiné direct (`?filter=amp` limite aux participants " & ") ET pour diagnostiquer un mauvais choix de matchup racine (voir bug `isRootMatchup` ci-dessus).
- `/backfill-pinnacle` — rattrapage ponctuel décrit plus haut. **Déclenche de vrais posts Telegram**, à utiliser consciemment.

## Pour démarrer une nouvelle session sereinement

1. Vérifier `/errors` sur les deux workers — un bug silencieux peut traîner depuis des heures.
2. Vérifier `/current` sur les deux — voir ce qui est actif, si quelque chose semble étrange (ex: `eventName` vide → probablement un combo schedule).
3. Si l'utilisatrice signale une ligne absente/fausse : ne jamais bloquer sur Pinnacle. Tester **rapidement** les 4 sources une par une (`/test-pinnacle`, `/test-piwi-teams`, `/test-matchbook-teams`, `/test-oddsportal-teams`), puis `/test-monitoring-message` pour voir ce qui a été RÉELLEMENT envoyé.
4. Après chaque fix déployé, penser à `/backfill-pinnacle` si des cotes déjà actives sont concernées.
